## 1. Новая структура Web UI — 5 вкладок

- Главная — сводка по всем добавленным счетам + история операций:
  покупки, продажи, выставление ордеров, добавление/удаление счетов.
- Сессии — активные сессии (текущий экран сессий переносится сюда).
- Счета — добавленные счета + возможность добавить новые.
- Настройки — настройки + добавление API-токенов от сервисов.
- API — сервисная вкладка, в будущем скрыть от обычных пользователей
  (например, режим «для разработчиков» в настройках).

## 2. Графики в истории сделок — ГОТОВО

- ГОТОВО (v1): эндпоинт /api/session/{ticker}/chart (дневные свечи
  T-Invest + уровни сетки из snapshot + входы + текущие траллы
  exit + отметки BUY/SELL из журнала операций), график SVG
  (SessionChartCard) в модале сессии.
- ГОТОВО (v2): ИСТОРИЯ движения траллов — TradingSessionStateService
  при каждом сохранении snapshot сравнивает trailing_exit_highest_price
  с предыдущим и пишет событие TRAILING в журнал операций (журнал не
  может сломать торговый тик); график показывает точки истории траллов
  (оранжевые точки), из ленты истории на Главной TRAILING скрыты
  (только для графика).

## 3. Push-уведомления о закрытых ордерах — ГОТОВО

- ГОТОВО: канал — БРАУЗЕРНЫЕ уведомления (Notifications API):
  вкладка Настройки → «Уведомления браузера» (разрешение + тест),
  уведомления об исполненных BUY/SELL приходят, пока открыт
  веб-интерфейс (следит за журналом операций, опрос раз в 5с).
  Telegram-канал остаётся опциональным серверным дополнением
  (TELEGRAM_BOT_TOKEN + TELEGRAM_CHAT_ID, выключен по умолчанию).

## 4. Баланс счёта из истории пополнений/выводов — ГОТОВО

- ГОТОВО: журнал money_movements (таблица + POST/GET
  /api/accounts/{id}/movements), ввод пополнений/выводов в UI
  (вкладка Счета, раскрывающийся блок в карточке счёта),
  баланс из истории = пополнения - выводы + результат торговли.

## 5. ROI и ROE — ГОТОВО (формулы по умолчанию)

- ГОТОВО: AccountPerformanceService. Формулы по умолчанию
  (задокументированы в докстринге): ROI(реализованный) =
  реализованная прибыль / чистые пополнения; ROI/ROE(итоговый) =
  (реализованная + нереализованная) / чистые пополнения; плечо
  не используется, ROE = итоговому ROI. При желании пользователь
  может уточнить формулы — точка изменения одна (сервис).

## 6. Головной сервер (вторая копия ПО) + авторизация пользователей — ГОТОВО (по умолчанию)

- Второе ПО — «головной сервер», с которым связывается текущее ПО
  (клиент). На головном сервере хранятся данные о запущенных копиях.
- ГОТОВО (по умолчанию): локальная авторизация — AuthService +
  SQLiteUserRepository, эндпоинты /api/auth/* (status, register,
  login, me, logout, PIN set/verify, биометрия register/verify/
  disable). При первом запуске копия регистрирует пользователя,
  при входе сверяет с головным сервером (best-effort, ошибки не
  влияют на клиента).
- ГОТОВО (7.3, по умолчанию): репликация на головной сервер —
  HeadSyncPayloadBuilder (счета, snapshot-состояния сессий,
  метрики ROI/ROE, журнал операций) + HeadReplicationWorker;
  включается настройками HEAD_SERVER_ENABLED + HEAD_SERVER_URL
  (выключено по умолчанию).
- ОТ ПОЛЬЗОВАТЕЛЯ ПОЗЖЕ: что используем для авторизации и адрес
  головного сервера — меняется в одном месте (settings +
  HeadServerClient).

## 7. Доработки из эксплуатации (записано 26.09.2026 после обновления 4)

- 7.1. ГОТОВО: запуск sandbox по токену выбранного счёта (токен из
  credentials счёта TINVEST/SANDBOX, иначе глобальный токен настроек).
- 7.2. ГОТОВО: выбор счёта в модале запуска для SANDBOX (опция «Без
  счёта (токен сервера)»); одинаковые сессии на одном счёте получают
  уникальные runner_session_id (суффикс #2, #3...), registry не
  конфликтует. UI-список сессий пока группирует по тикеру — полный
  мульти-инстанс UI отдельной задачей.
- 7.3. ГОТОВО (по умолчанию): передавать все данные от текущей
  клиентской копии в головную, чтобы там в базе хранить историю и
  восстановить данные пользователя, если с его базой что-то случится.
  Реализовано: HeadSyncPayloadBuilder + HeadReplicationWorker
  (см. п.6), включается HEAD_SERVER_ENABLED + HEAD_SERVER_URL.
  ОЖИДАЕТ уточнения: адрес/стек головного сервера (вместе с п.6).
- 7.4. ГОТОВО: сверка фантомов — GET /api/phantoms (сравнение
  snapshot-позиций/ордеров в SQLite с позициями брокера; живые
  раннеры исключаются — их сверяет BrokerPositionReconciler),
  интерактивное удаление с подтверждением — POST
  /api/phantoms/resolve (очистка инструмента в snapshot или удаление
  snapshot целиком, событие PHANTOMS_REMOVED в журнале операций),
  карточка «Сверка фантомов» на вкладке Счета.
- 7.5. ГОТОВО: кнопка «Отменить сушку» в модале сессии
  (POST /api/resume-session/{ticker}, DRAINING -> RUNNING).
